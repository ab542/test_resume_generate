# 性能测试面试总结（基础知识+实际场景）

---

## 一、基础概念

### 1. 什么是性能测试？
性能测试是通过模拟用户并发请求，测试系统在不同负载下的性能表现，找出系统性能瓶颈，验证系统是否满足业务性能需求。

**核心目标：**
- 发现系统性能瓶颈
- 验证系统是否能支撑预期用户量
- 评估系统稳定性
- 为架构优化提供数据依据

---

### 2. 核心性能指标

| 指标 | 含义 | 怎么理解（业务场景举例） |
|------|------|-------------------------|
| **响应时间（RT）** | 从发送请求到收到响应的时间 | 用户点击搜索，多久能看到结果。一般要求接口响应 < 200ms，页面 < 2s |
| **TPS** | 每秒事务数 | 系统每秒能处理多少笔业务（比如订单提交）。TPS越高性能越好 |
| **QPS** | 每秒查询数 | 每秒能处理多少个查询请求，和TPS类似，查询场景用得更多 |
| **并发数** | 同时在线/同时请求的用户数 | 秒杀活动，同时有10000用户进来抢，系统能不能扛住 |
| **吞吐量** | 单位时间处理请求数 | 和TPS/QPS意思相近，体现系统处理能力 |
| **错误率** | 失败请求占比 | 压测时错误率要 < 0.1%，错误率高说明系统扛不住了 |
| **95线/99线响应时间** | 95%/99%的请求响应时间不超过这个值 | 关注长尾请求，比如平均响应100ms，但99线有2s，说明还有少量请求很慢，用户体验不好 |

**面试常问：平均响应时间 vs 95线怎么选？**
- 平均会被快请求拉低，95线更能反映真实用户体验
- 一般要看95线或者99线，保证绝大多数用户体验合格

---

### 3. 性能测试分类

| 类型 | 目的 | 场景举例 |
|------|------|---------|
| **负载测试** | 逐步增加负载，看系统在不同负载下的表现，找到性能拐点 | 系统预期支撑500并发，从100→200→500→800逐步加压，看什么时候性能下降 |
| **压力测试** | 用超过预期的负载压，看系统最大能扛到多少，什么时候崩溃 | 秒杀活动，预期5000并发，用10000并发压，看系统会不会挂，能不能自动恢复 |
| **并发测试** | 模拟多个用户同时访问同一个接口，考验并发下数据一致性 | 优惠券并发领取，会不会超卖；库存并发扣减，会不会扣成负数 |
| **稳定性测试** | 长时间用恒定负载跑，看系统稳定性，有没有内存泄漏 | 系统要稳定跑7×24小时，用100并发跑24小时，看内存会不会一直涨，会不会慢慢变慢 |
| **容量测试** | 测试系统能承载的最大数据量，大数据量下性能表现 | 数据库表到1000万行，查询性能怎么样；日志存100G，查询会不会很慢 |
| **基准测试** | 系统优化前先跑一遍基准，优化后再对比，看优化效果 | 加索引前跑一遍查询性能，加索引后再跑，对比提升多少 |

---

## 二、性能测试流程

```
1. 需求分析 → 确定性能指标（要满足多少TPS，响应时间多少）
2. 制定方案 → 选工具、设计场景、确定压测环境
3. 编写脚本 → 用工具编写压测脚本，设置参数
4. 执行压测 → 逐步加压，监控各项指标
5. 分析结果 → 看指标是否达标，找瓶颈
6. 优化调优 → 开发优化完，再复测验证
```

**实际项目例子：**
> 项目要上线618活动，运营说预计同时在线1万人，峰值TPS 2000，要求接口响应 < 500ms，错误率 < 0.1%。我们按照这个指标做压测，不达标就优化，达标再上线。

## 三、常用性能测试工具

### 1. JMeter（最常用，功能强大）

**优点：**
- 免费开源，功能强大，支持各种协议（HTTP、TCP、JDBC等）
- 图形化界面，脚本编写快
- 插件丰富，支持各种监查看结果

**缺点：**
- 高并发下本身比较耗资源，单机并发能力不如Locust/Gatling
- 用Java写，二次开发不方便

**常用组件：**
- 线程组：设置并发数、循环次数
- HTTP请求：定义接口URL、参数、头
- 断言：判断响应是否正确
- 查看结果树：看单个请求响应
- 聚合报告：看统计数据（平均RT、95线、TPS）
- 监听器：生成结果图表

---

### 2. Locust（Python写，代码方式定义场景）

**特点：**
- 用Python代码写压测脚本，灵活
- 分布式压测方便，支持几万并发
- WebUI界面，实时看结果
- 适合懂代码的测试开发

**脚本例子：**
```python
from locust import HttpUser, task, between

class UserBehavior(HttpUser):
    wait_time = between(1, 3)  # 每个请求之间等1-3秒
    
    @task
    def get_user(self):
        self.client.get("/api/user/1")
    
    @task
    def search_product(self):
        self.client.get("/api/products?keyword=test")
```

---

### 3. Gatling（基于Scala，高并发性能好）

**特点：**
- 基于Akka异步框架，单机并发能力强
- 生成HTML报告很漂亮
- 适合高并发场景

---

### 4. 系统监控工具

压测的时候需要同时监控系统各项指标：

| 监控对象 | 常用命令/工具 | 关注什么 |
|---------|--------------|---------|
| **服务器CPU** | `top`、`htop` | CPU使用率超过80%说明有瓶颈 |
| **服务器内存** | `free -h`、`top` | 内存使用率，有没有OOM |
| **磁盘IO** | `iostat`、`df -h` | IO等待是不是很高，磁盘满了吗 |
| **网络** | `ifstat`、`netstat` | 网络带宽够不够，连接数是不是太多 |
| **数据库** | MySQL慢查询日志、`show processlist` | 慢查询、锁等待、连接数打满 |
| **JVM（Java应用）** | jstack、jmap、VisualVM | GC频率、堆内存使用、线程死锁 |

**实际场景：** 压测的时候，发现CPU跑到100%，TPS上不去，说明CPU有瓶颈，需要看是哪部分代码占用CPU高。

## 四、实际项目性能测试场景举例

### 场景一：秒杀/优惠券活动并发测试

**需求：**
- 活动发100张优惠券，1000用户同时抢，不能超卖
- 要求：TPS能到500，响应时间 < 500ms，错误率 < 0.1%

**压测设计：**
1. 用JMeter设置1000并发线程
2. 每个线程循环请求抢优惠券接口
3. 监控：
   - TPS、响应时间、错误率
   - 服务器CPU、内存
   - 数据库连接数、锁等待

**可能发现的问题：**
- 没有加分布式锁，1000并发抢，最后发出去150张，超卖了
- 数据库锁粒度太大，导致很多请求超时，错误率高
- Redis缓存没做好，大量请求打到数据库，数据库CPU跑满

---

### 场景二：大数据量查询性能测试

**背景：**
- 项目中粉丝日志表，数据量已经到千万级
- 查询接口原来快，现在越来越慢，需要压测优化

**测试过程：**
1. 造数据：把数据库表数据量造到1000万行
2. 设计场景：不同条件组合查询
3. 执行压测：100并发，看查询响应时间

**可能发现的问题：**
- 没用索引，全表扫描，查询要10s+
- 索引建了，但没用到最左前缀，还是慢
- 分页深度翻页，`LIMIT 1000000, 10` 性能很差
- 没有分页，一次查几万条，导致OOM

**优化后验证：**
- 加了正确索引，查询从10s降到200ms以内
- 压测验证，100并发下95线响应 < 300ms，达标

---

### 场景三：接口导出功能性能测试

**背景：**
- 用户要导出10万行报表，原来POI导出OOM，优化成EasyExcel，需要验证

**测试：**
1. 模拟导出10万行数据
2. 监控内存变化
3. 看导出时间

**结果对比：**
- 原来POI：内存占用800MB+，10万行直接OOM
- 优化后EasyExcel：内存占用100MB以内，10万行能稳定导出

---

### 场景四：系统稳定性测试

**需求：**
- 新版本上线，要验证系统能稳定跑7×24小时不宕机

**做法：**
1. 用日常峰值TPS的1.5倍恒定负载
2. 连续压测24小时
3. 监控：
   - 内存变化（有没有持续上涨，判断内存泄漏）
   - 错误率（会不会跑着跑着错误率升高）
   - 响应时间（会不会越来越慢）

**可能发现：**
- 连接池用完了没释放，跑几个小时后没连接可用，所有请求报错
- 内存泄漏，跑24小时内存从2GB涨到5GB，最后OOM

---

## 五、常见性能瓶颈排查思路

### 排查步骤（从上到下）：

```
1. 先看网络带宽：带宽跑满了吗？带宽不够先升级带宽
2. 再看服务器CPU：CPU使用率是不是100%？
   - CPU高：看是应用代码占的，还是数据库占的
   - 如果是数据库CPU高：基本就是慢查询，加索引优化
3. 再看内存：内存够不够？有没有OOM？内存泄漏？
4. 再看磁盘IO：IO等待是不是很高？是不是频繁刷盘？
5. 最后看数据库：
   - 有没有慢查询？
   - 有没有锁等待？
   - 连接数打满了吗？
   - 连接池配置对不对？
```

### 常见性能瓶颈举例：

| 现象 | 可能原因 | 优化方向 |
|------|---------|---------|
| TPS上不去，CPU100% | 代码有计算密集型逻辑，或者SQL没索引 | 优化算法，SQL加索引 |
| TPS上不去，CPU很低 | 瓶颈不在CPU，可能是锁等待、IO阻塞、数据库慢 | 看锁等待，优化SQL，增加缓存 |
| 响应时间越来越长，内存持续涨 | 内存泄漏，连接没释放 | 检查连接池、线程池是否正确释放 |
| 并发高了错误率升高 | 连接池满了，线程池满了，数据库连接不够 | 调大连接池参数，优化连接复用 |
| 同样并发，第一次快，后面越来越慢 | 缓存没命中，都打到数据库 | 优化缓存策略，增加缓存命中率 |

## 六、面试常见问答

### Q1：你们项目性能测试流程是怎么做的？

**A：**
我一般按这个流程做：
1. **需求分析**：先和开发、产品确认，这次性能测试要达到什么指标，比如峰值多少TPS，响应时间要求多少，错误率要求多少
2. **场景设计**：确定要压哪些核心接口，是并发测试还是稳定性测试，用什么工具
3. **环境准备**：尽量和生产配置一致，数据量也要和生产差不多，不然压出来不准
4. **编写脚本**：JMeter写脚本，加断言验证结果对不对
5. **执行压测**：一般从低并发逐步升到高并发，同时监控服务器CPU、内存、数据库各项指标
6. **结果分析**：整理RT、TPS、95线、错误率这些数据，对比需求看是否达标，如果不达标，和开发一起排查瓶颈
7. **优化复测**：开发优化完，再压一遍验证优化效果，输出测试报告

**实际例子：** 我们618活动前，都会对秒杀接口、商品查询接口做性能测试，确认峰值5000并发下能扛住，才敢上线。

---

### Q2：怎么理解并发用户数和在线用户数区别？

**A：**
- **在线用户数**：只是挂在系统上，不一定同时发请求，比如1万用户打开网页放着不动，不算并发
- **并发用户数**：同时向服务器发请求，请求处理完成才是真正的并发

一般在线用户数 ≈ 10倍并发用户数（因为用户不是一直不停发请求，有思考时间），比如1万在线，实际并发大概1000。

---

### Q3：压力测试中，CPU使用率100%正常吗？

**A：**
不一定，要看情况：
- 如果CPU100%，同时TPS还能随着并发增加而增加，说明系统还能继续扛，只是CPU已经跑满，需要升级CPU或者优化代码
- 如果CPU100%，TPS上不去，响应时间变长，错误率升高，说明CPU已经成为瓶颈，必须优化

---

### Q4：你遇到过哪些性能问题？怎么排查解决的？

**可以按STAR说：**

**Situation（场景）：**
> 我们项目上线前压测广告数据报表查询接口，发现千万级数据下查询要10秒，远超要求的500ms，不达标。

**Task（任务）：**
> 需要排查性能瓶颈，协助开发优化，让查询性能达标。

**Action（行动）：**
> 1. 先看执行计划，发现SQL没走索引，因为查询条件是日期范围，而索引建在其他字段
> 2. 发现原SQL用了`DATE(create_time)`函数，导致索引失效
> 3. 和开发讨论，改成范围查询 `create_time between 'xxx' and 'xxx'`，然后对`create_time`加联合索引
> 4. 优化后重新压测

**Result（结果）：**
> 查询时间从10s+降到200ms以内，100并发下95线响应300ms，达标上线。

**另一个例子：**
> 压测秒杀抢优惠券，发现并发1000时错误率5%，查下来是数据库行锁范围太大，很多事务等待超时。优化后，把行锁粒度缩小到具体库存行，加上Redis分布式锁预扣库存，错误率降到0.1%以下。

---

### Q5：性能测试中，为什么要做逐步加压？

**A：**
1. 可以看到系统在不同并发下的性能变化曲线
2. 找到性能拐点：比如并发从100加到500，TPS线性增长，加到800后TPS不涨反而降了，错误率升了，说明800就是拐点，系统最大扛到500并发
3. 一下子压满高并发，出问题不好定位是哪一步出问题，逐步加压更容易观察变化

---

### Q6：JMeter怎么参数化？为什么要参数化？

**A：**
参数化就是让每个请求用不同的参数，比如测试登录，每个线程用不同的用户名密码，避免缓存影响，更真实模拟用户。

JMeter做法：
- 添加CSV数据文件设置
- 把测试数据写在CSV文件里
- 引用变量：`${username}`

---

### Q7：JMeter断言怎么用？

**A：**
断言用来判断请求结果是不是正确的，比如接口返回应该包含`"code": 0`，如果返回`"code": 1`说明请求失败，要统计到错误里。

常用：
- 响应断言：判断响应文本中有没有包含指定字符串
- JSON断言：判断JSON响应某个字段的值对不对

---

### Q8：什么是think time（思考时间）？为什么要加？

**A：**
思考时间就是用户做完一个操作后，看页面思考几秒再点下一个操作，模拟真实用户行为。
- 不加思考时间，线程会一直不停发请求，压力比实际用户大很多，压出来结果不准
- 一般设置1-3秒随机思考时间，更真实

---

### Q9：你们性能测试环境和生产一样吗？不一样怎么办？

**A：**
理想情况尽量配置和数据量和生产一致，这样结果准。如果硬件配置比生产低，可以按比例推算，或者发现瓶颈后让开发在预发生产环境再验证一次。

我们一般做法：测试环境配置是生产的1/4，数据量和生产一样，压测出结果后，推算生产能扛住，上线前在预发生产再压一遍核心场景。

---

### Q10：性能测试什么情况用分布式压测？

**A：**
单机并发能力不够的时候，比如你要压1万并发，单机CPU内存都跑满了，压不出来，这时候用分布式多台机器一起压。
- JMeter支持分布式，主节点控制，多个从节点发请求
- Locust分布式也很方便，启动多个worker节点就行

---

## 六、总结（软件测试对性能测试要求）

软件测试工程师做性能测试，重点掌握：
1. **基础概念**：能说清楚RT、TPS、QPS、95线这些指标含义
2. **工具使用**：JMeter会写脚本，会看聚合报告，会监控系统指标
3. **排查思路**：出了性能问题，知道从哪几步往下找瓶颈
4. **结合实际**：能说出来你在项目中做过什么性能场景，遇到什么问题，怎么解决的

不用太深究底层原理，重点是**你实际做过，有项目经验，能定位常见问题**。
