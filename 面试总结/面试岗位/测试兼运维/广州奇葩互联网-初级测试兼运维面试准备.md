## 二、软件测试基础（70%核心考察）

### 1. 说一下你对软件测试流程的理解？

**参考回答：**

```
完整的测试流程包括：

① 需求分析阶段
  - 参加需求评审，理解业务逻辑
  - 对需求不明确、有歧义的地方提出来
  - 评估测试范围和工作量

② 测试计划阶段
  - 制定测试策略（测什么、怎么测、谁来测）
  - 确定测试环境和测试数据准备方案
  - 评估风险和资源

③ 测试设计阶段
  - 编写测试用例（正常流程 + 异常场景 + 边界值）
  - 评审测试用例，查漏补缺
  - 准备测试数据

④ 测试执行阶段
  - 执行功能测试、兼容性测试、UI测试、接口测试
  - 提Bug到禅道/JIRA，跟踪Bug生命周期
  - 每日汇报测试进度

⑤ 测试报告阶段
  - 编写测试报告，总结测试覆盖率和Bug分布
  - 给出上线建议（是否满足上线标准）

⑥ 上线跟踪
  - 生产环境冒烟验证
  - 线上问题跟进
```

**面试金句**："测试不是只找Bug，而是保障质量的全流程参与。从需求阶段就开始介入，能提前预防很多问题。"

### 2. 你怎么设计一个功能的测试用例？

**参考回答（按方法论说）：**

```
我会用以下方法组合设计用例：

① 等价类划分——把输入数据分成有效等价类和无效等价类
  举例：用户名长度限制6-20位

② 边界值分析——等价类的边界最容易出Bug
  举例：长度5、6、20、21，金额0、0.01、最大值

③ 场景法——模拟真实用户操作流程
  举例：注册→登录→浏览→加购→下单→支付

④ 错误推测法——根据经验补充容易出问题的点
  举例：网络中断、快速双击、特殊字符输入

实际用例模板：
  用例编号 | 模块 | 前置条件 | 操作步骤 | 预期结果 | 优先级
```

### 3. Bug的生命周期是什么样的？你在禅道/JIRA上怎么管理？

**参考回答：**

```
Bug生命周期：

  新建(New) → 确认(Confirmed) → 已分配(Assigned)
  → 修复中(In Progress) → 已修复(Fixed/Resolved)
  → 已验证(Verified) → 已关闭(Closed)

  如果验证不通过，重新打开(Reopen)回到已分配状态
  如果开发认为不是Bug，标记为拒绝(Rejected)或暂缓(Deferred)

我在禅道上的管理方式：
  - 提Bug时写清楚：标题（简明描述问题）、操作步骤、预期结果、
    实际结果、截图/日志附件、环境信息（浏览器版本、操作系统）
  - 严重程度分级：致命>严重>一般>轻微>建议
  - 优先级：紧急>高>中>低
  - 每天跟踪自己提的Bug状态，修复后24小时内验证
  - 验证通过后关闭，验证不通过重新打开并附上复现截图
```

### 4. 功能测试、兼容性测试、UI测试、接口测试的区别和侧重点？

| 测试类型 | 关注点 | 常用工具 |
|---------|--------|---------|
| 功能测试 | 功能是否正确实现，业务流程是否跑通 | 禅道/Testlink管理用例 |
| 兼容性测试 | 不同浏览器/操作系统/分辨率下能否正常使用 | BrowserStack/虚拟机 |
| UI测试 | 页面布局、文字、颜色、交互是否符合设计稿 | 像素对比工具/肉眼对比 |
| 接口测试 | 接口请求响应是否正确，异常处理是否完善 | Postman/JMeter |

**面试金句**："这四种测试各有侧重，实际项目中会组合使用。比如一个新功能，我先做功能测试确保逻辑正确，再测不同浏览器的兼容性，最后用Postman验证接口在各种异常入参下的表现。"

### 5. 如果你發現一個Bug，但開發說"這不是Bug，是需求設計的"，你怎麼處理？

**参考回答：**

```
第一步：冷靜確認。回到需求文檔核對，確認這個行為是否真的不符合需求。

第二步：如果需求沒有明確說明：
  - 從用戶角度分析——這個行為會不會讓用戶困惑或誤操作？
  - 對比同類產品——業界通常怎麼處理？
  - 評估影響範圍——如果上線，會有多少用戶受影響？

第三步：根據分析結果決定：
  - 確實是需求問題 → 找產品經理確認，如果需要改，提需求變更
  - 是體驗問題不是功能問題 → 和開發溝通，建議優化，優先級可適當降低
  - 確認不是問題 → 關閉Bug，但記錄到測試報告中供參考

關鍵是：對事不對人，拿數據和用戶體驗說話，而不是主觀爭論。
```

### 6. 你覺得一個好的測試報告應該包含哪些內容？

```
① 測試概況：測試範圍、測試時間、測試人員、測試環境
② 用例執行統計：總用例數、執行數、通過數、失敗數、阻塞數、通過率
③ Bug統計：
   - 按嚴重程度分布（致命/嚴重/一般/輕微）
   - 按模塊分布（哪個模塊Bug最多）
   - Bug狀態分布（已修復/未修復/拒絕/暫緩）
④ 遺留風險：未修復的Bug及其影響評估，給出建議
⑤ 測試結論：是否滿足上線標準，需要什麼條件才能上線
```

### 7. 說一下你常用的Linux命令，每個是用來做什麼的？

**参考回答（按场景说，不要说流水账）：**

```
日志排查场景：
  tail -f app.log          # 实时查看日志，调试时最常用
  tail -100 app.log        # 看最后100行，快速定位最近的错误
  grep "ERROR" app.log     # 过滤错误日志
  grep -rn "NullPointer" /var/log/  # 递归搜索所有日志中的异常

  ps -ef | grep java       # 看Java进程有没有启动

文件操作场景：
  ls -al                   # 查看文件权限和大小

网络/端口场景：
  netstat -anp | grep 8080  # 看端口被哪个进程占用
  curl http://localhost:8080/health  # 验证服务是否启动成功

资源监控场景：
  df -h                    # 看磁盘有没有满
  free -h                  # 看内存够不够
```

### 8. 應用部署到服務器上失敗了，你怎麼排查？

**参考回答（排查步骤）：**

```
第一步：确认部署包是否正确
  - ls -al 查看部署包的完整性和大小，确认不是空文件或损坏文件
  - md5sum app.jar 核对文件MD5，确认传输过程没有问题

第二步：确认端口和进程
  - netstat -anp | grep 8080  查看目标端口是否被占用
  - 如果被占用，ps -ef | grep java 找到进程，确认是否需要 kill

第三步：查看启动日志
  - cd /var/log/app && tail -f app.log  实时看启动日志
  - 搜索ERROR和Exception关键字定位具体报错

第四步：常见问题逐个排查
  - df -h  磁盘满了？→ 清理日志腾空间
  - free -h  内存不够？→ 关掉非必要进程
  - java -version  JDK版本不对？→ 检查环境变量
  - cat /etc/nginx/nginx.conf  Nginx配置冲突？→ 检查端口和代理规则
  - telnet db-host 3306  数据库连不上？→ 检查网络和安全组

第五步：回滚
  - 如果短时间无法解决，mv app.bak app.jar 先回滚到旧版本
  - 保证服务可用，然后离线排查
```

### 9. 線上環境突然出現大量500錯誤，你怎麼應對？

**参考回答（应急场景）：**

```
第一時間（止血，不是排查）：
  ① 确认影响范围：是所有用户还是部分用户？所有接口还是某个接口？
  ② 如果有回滚机制，评估是否先回滚到上一个稳定版本
  ③ 如果没有回滚，评估是否先重启服务临时恢复

快速排查：
  ① 先看应用日志，锁定错误堆栈：
     tail -500 app.log | grep -A 20 "ERROR\|Exception"
  ② 看数据库连接是否正常：
     telnet db-host 3306
     查数据库连接数：SHOW PROCESSLIST; 看是否有大量锁等待
  ③ 看服务器资源：
     top → CPU/内存是否打满
     df -h → 磁盘是否满了
     free -h → 内存是否OOM
  ④ 看是否有最近的代码发布或配置变更：
     git log --oneline -5 → 最近提交了什么
  ⑤ 看是否有突发流量：
     查Nginx access.log统计QPS

修复后：
  ① 在测试环境复现并验证修复
  ② 确认修复后不再出现
  ③ 写复盘文档，记录根因和改进措施
```

**面试金句**："线上问题排查的核心原则：先恢复服务，再定位根因。用户不关心你为什么挂，只关心什么时候好。"

### 10. 你怎麼保證測試環境數據庫的安全？數據備份你是怎麼做的？

**参考回答：**

```
日常安全管理：
  ① 测试环境数据库密码和生产环境完全隔离，不能用一样的
  ② 定期清理敏感数据（用户手机号、身份证号脱敏）
  ③ 限制数据库访问IP，只允许内网访问
  ④ 给开发和测试分配最小权限账号，不用root

备份策略：
  ① 定时备份：
     - 用 mysqldump 每天凌晨自动备份
     - crontab 定时任务：0 2 * * * /data/backup/backup.sh
  ② 备份脚本示例：
     mysqldump -u backup_user -p'xxx' --single-transaction \
       --databases test_db | gzip > /data/backup/test_db_$(date +%Y%m%d).sql.gz
  ③ 保留最近7天的备份，过期自动清理（脚本里加 find + rm）
  ④ 定期做恢复演练，确保备份文件是可用的（不少公司备份了但恢复不了）

数据初始化：
  - 每次功能测试前，执行初始化SQL脚本把数据恢复到基线状态
  - 用 source /data/sql/init_test_data.sql 一键初始化
```

### 11. 你寫過什麼自動化運維腳本？舉一個具體例子。

**参考回答（Shell 脚本示例，要能讲清楚逻辑）：**

```bash
#!/bin/bash
# 一键启停测试环境脚本
# 场景：每天测试前启动环境，下班后关掉节省资源

APP_NAME="test-app"
JAR_PATH="/opt/app/test-app.jar"
LOG_PATH="/var/log/app/test-app.log"
BACKUP_DIR="/opt/app/backup"

case "$1" in
  start)
    echo "正在启动 $APP_NAME ..."
    # 检查是否已经启动
    pid=$(ps -ef | grep $APP_NAME | grep -v grep | awk '{print $2}')
    if [ -n "$pid" ]; then
        echo "$APP_NAME 已在运行中，PID: $pid"
        exit 0
    fi
    # 启动应用
    nohup java -jar $JAR_PATH > $LOG_PATH 2>&1 &
    sleep 5
    # 验证启动
    pid=$(ps -ef | grep $APP_NAME | grep -v grep | awk '{print $2}')
    if [ -n "$pid" ]; then
        echo "$APP_NAME 启动成功，PID: $pid"
    else
        echo "$APP_NAME 启动失败，请查看日志"
        tail -20 $LOG_PATH
    fi
    ;;

  stop)
    echo "正在停止 $APP_NAME ..."
    pid=$(ps -ef | grep $APP_NAME | grep -v grep | awk '{print $2}')
    if [ -z "$pid" ]; then
        echo "$APP_NAME 未在运行"
        exit 0
    fi
    kill -15 $pid  # 优雅关闭
    sleep 10
    # 如果还没停，强制kill
    pid=$(ps -ef | grep $APP_NAME | grep -v grep | awk '{print $2}')
    if [ -n "$pid" ]; then
        kill -9 $pid
        echo "$APP_NAME 被强制关闭"
    else
        echo "$APP_NAME 已正常关闭"
    fi
    ;;

  restart)
    $0 stop
    $0 start
    ;;

  *)
    echo "用法: $0 {start|stop|restart}"
    exit 1
    ;;
esac
```

**讲解要点**：
- 为什么用 `kill -15` 而不是直接 `kill -9`？让应用有时间做收尾工作（关闭连接、保存状态）
- 为什么有 `sleep`？等进程真正起来/关闭
- 为什么有启动验证？启动不代表成功，要确认进程在不在

### 12. 寫一個日誌清理的定時任務腳本。

```bash
#!/bin/bash
# 清理7天前的日志，保留最近7天
# crontab：0 3 * * * /opt/scripts/clean_logs.sh

LOG_DIR="/var/log/app"
DAYS_TO_KEEP=7

# 删除超过指定天数的日志
find $LOG_DIR -name "*.log" -mtime +$DAYS_TO_KEEP -exec rm -f {} \;

# 压缩昨天之前的日志（不是删除，是节约空间）
find $LOG_DIR -name "*.log" -mtime +1 -exec gzip {} \;

# 记录清理结果
echo "$(date '+%Y-%m-%d %H:%M:%S') 日志清理完成" >> /var/log/cleanup.log
```

### 13. CentOS 上部署一個 Java 應用的完整流程

以 Spring Boot 項目為例，從零到能訪問：

**第一步：安裝基礎環境**

```bash
# JDK 11
yum install -y java-11-openjdk-devel
java -version

# MySQL
yum install -y https://dev.mysql.com/get/mysql80-community-release-el7-3.noarch.rpm
yum install -y mysql-server
systemctl start mysqld
systemctl enable mysqld

# 改初始密碼（CentOS MySQL 首次啟動會生成隨機密碼）
grep 'temporary password' /var/log/mysqld.log
mysql -u root -p
ALTER USER 'root'@'localhost' IDENTIFIED BY 'YourNewPass123!';
CREATE DATABASE myapp_db;
```

**第二步：上傳部署包**

```bash
# 方式一：scp 從本地傳上去
scp target/myapp-1.0.jar root@192.168.1.100:/opt/app/

# 方式二：CI/CD 自動推送（見下一節）
```

**第三步：配置 + 啟動**

```bash
cd /opt/app

# 後台啟動（核心命令）
nohup java -Xms512m -Xmx1024m -jar myapp-1.0.jar > app.log 2>&1 &

# 參數說明：
# nohup   → 終端關了服務也不停
# -Xms512m -Xmx1024m → 初始/最大堆內存
# > app.log → 標準輸出寫到 app.log
# 2>&1    → 錯誤輸出也寫到同一個文件
# &       → 後台運行
```

**第四步：驗證**

```bash
ps -ef | grep myapp                           # 進程在不在
netstat -anp | grep 8080                      # 端口在監聽嗎
curl http://localhost:8080/health             # 接口通不通
tail -f app.log                               # 有無報錯
```

**第五步：寫啟停腳本（避免每次手敲）**

```bash
#!/bin/bash
# /opt/app/app.sh
APP_NAME="myapp"
JAR="/opt/app/myapp-1.0.jar"
LOG="/opt/app/app.log"

case $1 in
  start)
    pid=$(ps -ef | grep $JAR | grep -v grep | awk '{print $2}')
    if [ -n "$pid" ]; then
        echo "$APP_NAME 已在運行 (PID: $pid)"
        exit 0
    fi
    nohup java -Xms512m -Xmx1024m -jar $JAR > $LOG 2>&1 &
    sleep 5
    pid=$(ps -ef | grep $JAR | grep -v grep | awk '{print $2}')
    [ -n "$pid" ] && echo "啟動成功 (PID: $pid)" || echo "啟動失敗，請查看 $LOG"
    ;;
  stop)
    pid=$(ps -ef | grep $JAR | grep -v grep | awk '{print $2}')
    [ -z "$pid" ] && echo "未運行" && exit 0
    kill -15 $pid        # 優雅關閉
    sleep 10
    pid=$(ps -ef | grep $JAR | grep -v grep | awk '{print $2}')
    [ -n "$pid" ] && kill -9 $pid && echo "已強制關閉" || echo "已正常關閉"
    ;;
  restart)
    $0 stop && $0 start
    ;;
  *)
    echo "用法: $0 {start|stop|restart}"
    ;;
esac
```

```bash
chmod +x /opt/app/app.sh
./app.sh start    # 啟動
./app.sh stop     # 停止
./app.sh restart  # 重啟
```

**第六步：配置開機自啟（systemd）**

```bash
vim /etc/systemd/system/myapp.service
```

```ini
[Unit]
Description=My Application
After=network.target mysqld.service

[Service]
Type=simple
User=root
WorkingDirectory=/opt/app
ExecStart=/usr/bin/java -Xms512m -Xmx1024m -jar /opt/app/myapp-1.0.jar
Restart=on-failure

[Install]
WantedBy=multi-user.target
```

```bash
systemctl daemon-reload
systemctl enable myapp       # 開機自啟
systemctl start myapp        # 立即啟動
systemctl status myapp       # 查看狀態
```

**發布新版本 + 回滾操作：**

```bash
# 1. 停服務
/opt/app/app.sh stop

# 2. 備份舊版本（mv 只是改名，不佔額外磁盤空間）
mv myapp-1.0.jar myapp-1.0.jar.bak

# 3. 上新版本，啟動
/opt/app/app.sh start
tail -f app.log    # 看日誌確認

# 4. 如果新版本掛了，秒級回滾
/opt/app/app.sh stop
mv myapp-1.0.jar.bak myapp-1.0.jar
/opt/app/app.sh start
```

**面試時不要背命令，按這個思路講：**

> 安裝環境(yum) → 上傳包(scp) → 後台啟動(nohup) → 驗證(curl) → 腳本化(啟停+回滾) → 開機自啟(systemd)

**Q：查詢訂單總金額大於1000的用戶，顯示用戶名和總金額**
```sql
SELECT u.username, SUM(o.amount) AS total_amount
FROM user u
INNER JOIN `order` o ON u.id = o.user_id
GROUP BY u.id, u.username
HAVING SUM(o.amount) > 1000;
```

**Q：LEFT JOIN 和 INNER JOIN 的區別？**
```
INNER JOIN：只返回兩張表中匹配的數據，不匹配的不顯示
LEFT JOIN：左表數據全部返回，右表沒匹配的顯示 NULL

舉例：
  用戶表有3個人(張三、李四、王五)，訂單表只有張三和李四有訂單
  INNER JOIN → 結果只有張三和李四（王五沒訂單不出來）
  LEFT JOIN → 張三、李四、王五都出來（王五的訂單字段為NULL）
```

**Q：WHERE 和 HAVING 的區別？**
```
WHERE：分組前過濾原始行數據
HAVING：分組後過濾聚合結果(COUNT/SUM/AVG)

舉例：
  WHERE status = 1 AND age > 18  → 先篩選條件再分組
  HAVING COUNT(*) > 10            → 分組後只保留數量大於10的組
```

### 15. 索引相關：什麼是索引？什麼時候索引會失效？

**参考回答：**

```
索引就像書的目錄，幫數據庫快速找到數據，不用全表掃描。

索引失效的常見場景：
  ① WHERE中對索引列用函數
     ❌ WHERE YEAR(create_time) = 2026
     ✓ WHERE create_time BETWEEN '2026-01-01' AND '2026-12-31'

  ② LIKE以%開頭
     ❌ WHERE username LIKE '%張%'
     ✓ WHERE username LIKE '張%'

  ③ 字符串不加引號（隱式類型轉換）
     ❌ WHERE phone = 13800000000  （phone是varchar）
     ✓ WHERE phone = '13800000000'

  ④ OR條件中不是所有列都有索引
     ❌ WHERE id=1 OR name='張三'  （name無索引）
     ✓ 拆分為兩條查詢，用UNION

  ⑤ 使用 != 或 <>
     大部分情況下不走索引

面試加分：可以提一句"不是索引失效就一定慢，如果數據量小，
全表掃描可能更快，最終要看EXPLAIN的結果。"
```

### 16. 手寫SQL場景題

**題目：有 user 表和 order 表，查詢每個用戶近30天的下單次數和總金額（包含沒下單的用戶）**

```sql
SELECT
    u.id,
    u.username,
    COUNT(o.id) AS order_count,
    COALESCE(SUM(o.amount), 0) AS total_amount
FROM user u
LEFT JOIN `order` o
    ON u.id = o.user_id
    AND o.created_at >= DATE_SUB(NOW(), INTERVAL 30 DAY)
    AND o.status = 'PAID'
GROUP BY u.id, u.username
ORDER BY total_amount DESC;
```

**注意點**：
- LEFT JOIN 保證沒下單的用戶也顯示（次數0、金額0）
- 過濾條件放在 ON 子句而非 WHERE，否則會把沒下單的用戶過濾掉
- COALESCE 把 NULL 轉成 0

### 20. CI/CD 自動化部署（加分項）

**為什麼不需要本地打包？**

手動部署是這樣：

```
本地 mvn package → scp 傳到服務器 → ssh 過去重啟
```

每次發布都要人工操作，容易出錯。正規團隊用的是 CI/CD 自動流水線：

```
你本地 git push 代碼
        │
        ▼
┌─────────────────────────────────────┐
│  CI/CD Pipeline 自動觸發             │
│                                     │
│  Stage 1: Build（編譯打包）          │
│    mvn clean package                │
│    → 產出 myapp-1.0.jar             │
│                                     │
│  Stage 2: Test（自動跑測試）         │
│    mvn test                         │
│    → 測試不通過？停止，通知你         │
│                                     │
│  Stage 3: Deploy（部署到服務器）      │
│    scp app.jar → 目標服務器           │
│    ssh 目標服務器 → 重啟服務          │
│                                     │
└─────────────────────────────────────┘
        │
        ▼
   測試環境更新完成，你去驗收
```

**兩種主流方案：**

| | GitLab CI | Jenkins |
|------|------|------|
| 配置方式 | 倉庫根目錄放 `.gitlab-ci.yml` | Jenkinsfile 或 Web 界面配置 |
| 觸發方式 | push 代碼自動觸發 | Git webhook 或定時觸發 |
| 運行環境 | 需要安裝 GitLab Runner | Jenkins 自身就是調度中心 |
| 適用場景 | 代碼託管在 GitLab，用全家桶 | 公司已有 Jenkins 基礎設施 |

**GitLab CI 配置示例（`.gitlab-ci.yml` 放在項目根目錄）：**

```yaml
stages:
  - build
  - test
  - deploy

# Stage 1：編譯打包
build:
  stage: build
  image: maven:3.8-openjdk-11          # 用 Maven 鏡像容器
  script:
    - mvn clean package -DskipTests
  artifacts:                            # 保留 jar 包，供後續 stage 用
    paths:
      - target/*.jar
  only:
    - main                              # 只有 main 分支 push 才觸發

# Stage 2：自動跑測試
test:
  stage: test
  image: maven:3.8-openjdk-11
  script:
    - mvn test
  only:
    - main

# Stage 3：部署到服務器
deploy:
  stage: deploy
  image: alpine:latest
  before_script:
    - apk add openssh-client           # 安裝 ssh/scp
  script:
    - scp target/*.jar root@192.168.1.100:/opt/app/
    - ssh root@192.168.1.100 "/opt/app/app.sh restart"
  only:
    - main
```

**關鍵概念總結：**

- **Git**：代碼版本管理。常用 `git clone/pull/commit/push`
- **Maven**：Java 項目構建工具。`mvn clean package` 一鍵打包
- **Jenkins / GitLab CI**：自動化流水線。代碼 push 後自動觸發構建→測試→部署
- **你測試要做的事**：push 之後看 pipeline 綠了還是紅了。綠了去測試環境驗收，紅了看日誌協調開發排查

### 21. Nginx/Tomcat/Spring Boot 部署（加分項）

**Q：Nginx 反向代理是什麼？你怎麼配置的？**

```
反向代理：客戶端請求先到Nginx，Nginx轉發給後端應用服務器，
         客戶端不知道後端服務器的真實地址。

好處：
  - 負載均衡：一個Nginx後面掛多台應用服務器
  - 安全：隱藏後端真實IP
  - 靜態資源：Nginx直接返回靜態文件，不用經過應用服務器

簡單配置示例：
server {
    listen 80;
    server_name test.example.com;

    # 靜態資源直接返回
    location /static/ {
        root /opt/app/;
    }

    # API請求轉發給後端
    location /api/ {
        proxy_pass http://localhost:8080;
    }
}
```

**Q：部署Spring Boot應用，常見問題有哪些？**
```
① 端口衝突：8080已經被佔用 → netstat -anp | grep 8080
② JDK版本不對：項目用JDK11，服務器裝的是JDK8 → java -version檢查
③ 配置文件沒更新：測試環境的application.yml沒改數據庫地址
④ 啟動內存不夠：java -jar -Xms512m -Xmx512m 指定堆內存
```

### 22. Postman / JMeter 接口測試（加分項）

**Q：你用Postman怎麼做接口測試？**

```
① 單接口測試：
   - 設置請求方法(GET/POST/PUT/DELETE)、URL、Headers、Body
   - 發送請求，檢查響應狀態碼和響應體
   - 用Tests標籤寫斷言，自動驗證返回值：
     pm.test("狀態碼200", () => pm.response.to.have.status(200));
     pm.test("返回成功", () => {
         const json = pm.response.json();
         pm.expect(json.code).to.equal(0);
     });

② 批量測試：
   - 用Collection管理一組接口
   - 用Runner一鍵跑整個Collection
   - 設置環境變量，切換測試/開發環境

③ 參數傳遞：
   - 登錄接口返回token → 提取到變量 → 後續接口自動帶上
```

**Q：JMeter 做壓力測試的基本思路？**
```
① 創建Thread Group：設置併發用戶數(比如100)、循環次數、啟動時間
② 添加HTTP Request：配置請求URL、參數
③ 添加Listener：查看結果樹、聚合報告(平均響應時間、吞吐量、錯誤率)
④ 運行後分析：看響應時間是否達標、有沒有錯誤、QPS是否滿足需求
```

### 场景1：测试环境数据库被開發誤刪了一張表，你怎麼處理？

```

  - 把這件事反饋給團隊，建議：
```

### 场景2：測試環境應用啟動後，一直報"數據庫連接失敗"

```

   SHOW PROCESSLIST; → 看當前連接數是不是滿了
```

### 23. "你怎麼同時處理測試和運維兩個角色的工作？"

**参考回答：**

```
這兩個角色其實是相輔相成的，不是割裂的。

  - 日常70%時間做測試：需求評審、寫用例、執行測試、提Bug

  - 用定時任務處理定期運維：備份、日誌清理自動化，不佔用工作時間

效率提升上：
  - 把重複運維工作腳本化（寫好啟動/停止/備份腳本），
    減少手動操作時間
  - 搭建好測試環境後，文檔化環境信息，
    減少同事環境問題來問我的頻率，減少打斷

實際好處：
  - 懂運維的測試，排查問題快——開發說"環境問題"甩鍋時，
    我能自己查日誌確認是真的環境問題還是代碼Bug
  - 測試時能提前發現部署相關的風險（配置缺失、端口衝突等）
```

### 25. "你怎麼跟開發溝通一個他們不認可的Bug？"

```
① 擺事實不擺態度
   - "你這裡有Bug" → 這是評價
   - "點擊這個按鈕後頁面沒反應，這是操作步驟和截圖" → 這是事實

② 評估優先級
   - 如果確實是小問題，可以商量調低優先級，後續版本修
   - 不糾結「是不是Bug」的標籤，聚焦「要不要修」

③ 找第三方裁決
   - 拉到產品經理一起看，讓產品決定這是不是預期行為
   - 拿競品對比，看行業通常做法

④ 記錄留存
   - 如果討論結果是「暫不修」，在Bug單上記錄原因和決策人
   - 避免後面出了問題說測試沒測到
```

## 附录：常见运维命令速查

```bash
# === 日志排查 ===
tail -f app.log                  # 实时跟踪日志
tail -100 app.log                # 最后100行
grep "ERROR" app.log             # 搜索错误
grep -A 5 "ERROR" app.log        # 搜索并显示后5行上下文
grep -rn "Exception" /var/log/   # 递归搜索目录

# === 进程管理 ===
ps -ef | grep java               # 找Java进程
kill -15 PID                     # 优雅关闭
kill -9 PID                      # 强制杀死
top                              # 实时资源查看

# === 端口/网络 ===
netstat -anp | grep 8080         # 端口占用查询
lsof -i:8080                     # 另一种端口查询
curl http://localhost:8080/health # 接口连通性测试
telnet db-host 3306              # 数据库端口測試
ping 192.168.1.1                 # 网络连通性

# === 资源监控 ===
df -h                            # 磁盘使用情况
free -h                          # 内存使用情况
du -sh /var/log/                 # 目录大小

# === 文件操作 ===
ls -al                           # 文件权限和大小
chmod +x script.sh               # 加执行权限
md5sum app.jar                   # 文件校验
scp app.jar user@host:/opt/      # 远程拷贝

# === 数据库 ===
mysqldump -u root -p db > backup.sql    # 备份
mysql -u root -p db < backup.sql        # 恢复
source /data/sql/init.sql               # 执行SQL文件

# === 定时任务 ===
crontab -e                       # 编辑定时任务
crontab -l                       # 查看定时任务
```
