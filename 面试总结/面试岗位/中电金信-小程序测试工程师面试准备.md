## 二、小程序基础与技术理解（重点准备）

### 1. 说一下你对微信小程序运行机制的理解？

**参考回答：**

```
微信小程序采用双线程架构：

渲染层（WebView）：负责页面渲染，使用 WXML/WXSS
逻辑层（JSCore）：负责业务逻辑，运行 JavaScript 代码

两层之间通过微信客户端（Native）作为中间层来通信，
数据通过 setData 从逻辑层传到渲染层，这是一个异步的过程。

关键理解：
- 每个页面都有自己的 WebView 实例
- 逻辑层只有一个，所有页面共享
- setData 不能太频繁，每次有大小限制（建议单次 < 256KB，每秒调用次数 < 20）
- 小程序基础库在微信客户端内，随微信版本更新
```

**面试金句**："小程序不同于 H5，它是双线程架构，渲染和逻辑分离。这个架构决定了它的性能优化方式和测试重点跟普通前端不同。"

### 2. 小程序测试和普通 H5/App 测试有什么不同？

| 维度 | H5 测试 | App 测试 | 小程序测试 |
|------|---------|----------|-----------|
| 运行环境 | 浏览器 | 操作系统原生 | 微信客户端内 |
| 版本依赖 | 无 | App 版本 | 微信版本 + 基础库版本 |
| 兼容性 | 浏览器兼容 | 系统版本 + 机型 | 微信版本 + 基础库版本 + 系统版本 |
| 审核机制 | 无 | 应用商店审核 | 微信审核 + 类目限制 |
| 包大小限制 | 无 | 有 | 严格（主包 2MB / 分包总 20MB） |
| 能力限制 | 浏览器 API | 系统 API | 微信 SDK API（受限） |
| 性能监控 | Lighthouse 等 | 自研/三方工具 | 微信开发者工具 Performance 面板 + 小程序后台 |
| 调试工具 | Chrome DevTools | Xcode/Android Studio | 微信开发者工具 + vConsole |

### 3. 你怎么理解小程序基础库？基础库更新后怎么测？

**参考回答：**

```
小程序基础库是微信客户端内提供的运行环境，包含：
- 小程序框架 API（wx.xxx）
- 组件渲染引擎
- 底层能力（网络、存储、地理位置等）

基础库版本的测试要点：
① 向前兼容——新基础库上跑的旧小程序有没有问题
② 向后兼容——老基础库能支持的功能在新代码里怎么降级
③ API 行为变更——wx.getSystemInfo 等接口返回值变化

我的测试方案：
1. 准备不同基础库版本的测试矩阵（高、中、低三个版本覆盖）
2. 维护一个测试 demo，覆盖常用 API 和组件
3. 每次基础库升级，跑一遍全量自动化用例
4. 重点关注 setData 渲染、组件生命周期、API 回调行为

实际测试中我会用微信开发者工具的「基础库版本切换」功能模拟不同版本。
```

### 4. 微信小程序常见的性能问题有哪些？怎么测试？

**参考回答（按优先级排列）：**

```
① setData 性能问题
  - 症状：页面卡顿、操作响应慢
  - 原因：频繁 setData、单次数据量大、setData 传了不需要的数据
  - 测试方法：微信开发者工具 Performance 面板，或用 wx.getPerformance() 
    获取渲染耗时，自动化脚本监控 setData 调用频率和数据大小

② 首屏加载慢
  - 症状：打开小程序白屏时间长
  - 原因：包体积大、首页接口多、图片未压缩
  - 测试方法：开发者工具 Network 面板记录加载时序，弱网环境测试，
    使用体验评分插件（audits）自动打分

③ 内存泄漏
  - 症状：长时间使用后小程序变卡、闪退
  - 原因：未销毁的定时器、未解绑的事件监听、闭包引用
  - 测试方法：长时间 monkey test，开发者工具 Memory 面板监控

④ 页面切换卡顿
  - 原因：onHide/onShow 里做了重操作
  - 测试方法：反复切换页面，监控帧率
```

**面试金句**："测小程序性能，setData 是第一优先级，因为它直接影响用户体验。我会在自动化用例里埋点监控 setData 的调用频率和数据量。"

## 三、测试方案设计与用例设计

### 5. 给你一个小程序功能需求，你怎么设计测试方案？

**参考回答（按流程说）：**

```
第1步：需求分析
  - 理解功能目标、业务流程、涉及的微信 API
  - 确认是否涉及基础库版本依赖（有些 API 要求特定版本以上）
  - 确认是否涉及分包、预加载等架构层面的设计

第2步：测试场景梳理
  - 正常场景：核心业务流程走通
  - 异常场景：网络异常、授权拒绝、接口超时、数据为空
  - 边界场景：输入长度、金额范围、并发操作
  - 微信特有场景：切后台回来、下拉刷新、分享进入、不同入口进入（扫码/公众号/转发）

第3步：测试矩阵设计
  - 微信版本 × 基础库版本 × 系统（iOS/Android）× 机型
  - 低版本基础库的降级表现
  - 不同屏幕尺寸适配（折叠屏、Pad）

第4步：自动化策略
  - 哪些用例做自动化（核心回归、兼容性遍历）
  - 用什么工具（minium / 微信开发者工具 CLI / 自建框架）

第5步：发布验证
  - 提审前 checklist 验证
  - 审核被拒的常见原因预检（类目、隐私协议、诱导分享等）
  - 灰度发布后的用户反馈监控
```

### 7. 小程序审核被拒的常见原因有哪些？你作为测试如何预检？

```
① 隐私合规
  - 是否在首次使用时弹起隐私协议
  - 是否在隐私协议中说明了收集的信息和用途
  - 测试方法：清除小程序数据后重新打开，检查隐私弹窗

② 类目不符
  - 小程序提供的内容是否和注册类目一致
  - 测试方法：对照微信小程序类目表自查

③ 诱导行为
  - 是否有诱导分享、诱导下载 App、诱导好评
  - 测试方法：检查所有页面按钮和文案

④ 功能不完整
  - 是否有空白页面、"功能开发中"占位
  - 测试方法：遍历所有页面和入口

⑤ 账号登录
  - 是否强制要求登录才能看任何内容
  - 微信要求：浏览类功能不得强制登录
```

### 8. 面试官可能会让你现场写一段小程序代码

```javascript
// pages/test/test.js
Page({
  data: {
    userInfo: null,
    list: []
  },

  onLoad(options) {
    this.fetchData()
  },

  fetchData() {
    wx.request({
      url: 'https://api.example.com/data',
      method: 'GET',
      success: (res) => {
        if (res.data.code === 0) {
          this.setData({ list: res.data.data })
        }
      },
      fail: (err) => {
        wx.showToast({ title: '请求失败', icon: 'none' })
      }
    })
  },

  onPullDownRefresh() {
    this.fetchData()
    wx.stopPullDownRefresh()
  }
})
```

**② 组件通信：**
```javascript
// 父组件 → 子组件：properties

Component({

  methods: {
    onTap() {
      this.triggerEvent('custom', { id: 1 })

  }

```

### 9. "你写自动化用例用什么框架？"

**参考回答：**

```
小程序自动化我用 minium（微信官方 Python 自动化框架）。

框架结构：
  minitest/
  ├── case/              ← 测试用例
  │   ├── test_login.py
  │   └── test_home.py
  ├── config.json        ← 项目配置（project_path、dev_tool_path）
  └── conftest.py

核心用例示例：
```python
import minium

class TestHomePage(minium.MiniTest):
    def test_page_load(self):
        """首页加载正常"""
        self.app.navigate_to('/pages/home/home')
        page = self.app.get_current_page()
        # 等待元素出现
        page.wait_for(10)  # 最多等 10 秒
        # 断言
        self.assertTrue(page.element_is_exists('.container'))
    
    def test_tab_switch(self):
        """底部 tab 切换正常"""
        page = self.app.get_current_page()
        page.get_element('.tab-item:nth-child(2)').tap()
        page.wait_for(2)
        self.assertEqual(
            page.get_element('.tab-item.active').text, 
            '消息'
        )
    
    def test_network_error_handling(self):
        """网络异常时的兜底展示"""
        # 模拟弱网
        self.app.mock_wx_method('request', result={'errMsg': 'timeout'})
        self.app.navigate_to('/pages/detail/detail?id=1')
        page = self.app.get_current_page()
        page.wait_for(5)
        # 应该有错误提示或重试按钮
        self.assertTrue(
            page.element_is_exists('.error-tip') or 
            page.element_is_exists('.retry-btn')
        )
```

**如果没写过 minium**，可以这样回答：
"我目前用 Python + Appium 做过移动端自动化，小程序自动化的思路跟 Appium 类似，都是通过操控元素来模拟用户操作。minium 我了解过，微信官方的框架，底层用的是微信开发者工具的远程调试能力，我上手应该快。"
```

### 12. "你怎么做小程序真机兼容性测试？"

**参考回答：**

```
兼容性测试矩阵：

| 维度 | 覆盖策略 |
|------|---------|
| iOS | 最新版 + 上一个大版本 |
| Android | 主流厂商（华为/小米/OPPO/vivo）+ 高/中/低端各一台 |
| 微信版本 | 最新版 + 用户量大的老版本 |
| 网络 | WiFi + 4G + 弱网（限速） |
| 场景 | 切后台回来、来电话中断、低电量模式 |

实际操作：
1. 重点机型真机测试，其他机型用云测平台（Testin/WeTest）
2. 微信开发者工具的「真机调试」功能，多台设备同时连接调试
3. 维护一份机型覆盖 checklist，每次发版前确认
```

## 六、用户反馈 & 线上问题跟进

### 13. "小程序发布后收到用户反馈崩溃/白屏，你怎么跟进？"

**参考回答：**

```
第一步：收集信息
  - 问用户：微信版本、手机型号、系统版本、操作步骤
  - 查后台：小程序后台 → 运维中心 → 错误日志/性能监控
  - 看时间段内有没有接口异常、基础库升级

第二步：尝试复现
  - 用相同机型+相同微信版本尝试复现
  - 如果涉及特定数据，造相同条件的数据
  - 弱网、内存不足等极端条件下复现

第三步：定位根因
  - 查看微信开发者工具的 sourceMap，定位到代码行
  - 检查是否某个 API 在低版本基础库不支持
  - 检查 setData 的数据量是否过大导致渲染卡死
  - 检查是否有未捕获的 Promise rejection

第四步：修复 + 验证 + 回归
  - 开发修完之后，验证修复效果
  - 在相同条件下跑一遍验证
  - 补充对应的回归用例

第五步：闭环
  - 在用户反馈系统中标记已解决
  - 如果影响面大，总结复盘文档
```

## 七、场景模拟题

### 第1题：给你一个「小程序分享卡片」功能，你准备怎么测？

> 我会从这几个维度测：
>
> **功能层面**：
> - 分享按钮是否正常出现（不同页面、不同状态）
> - 分享标题、图片、路径是否正确（onShareAppMessage 返回值）
> - 被分享者点击卡片能否正确进入目标页面并携带参数
> - 分享到不同场景：群聊、私聊、朋友圈（如有）
>
> **权限和隐私**：
> - 含敏感信息的页面是否应该禁用分享
> - 分享的图片是否符合微信规范
>
> **兼容性**：
> - iOS/Android 分享面板 UI 是否有差异
> - 低版本微信的分享行为
>
> **异常场景**：
> - 分享时网络断开
> - 分享后立即返回/杀进程
> - 被分享的目标页面参数被篡改（手动改 query 参数）
> - 分享的目标页面不存在或已下架

---

### 第2题：小程序首页加载很慢，你怎么分析和推动优化？

> 1. **先量化**：用微信开发者工具 Performance + Network 面板，记录首屏加载时间和各阶段耗时
>
> 2. **排查维度**：
>    - 包体积：主包是不是接近 2MB？图片有没有压缩？
>    - 接口：有几个请求？有没有串行调用可以改并行？
>    - 预加载：有没有用分包预加载（preloadRule）？
>    - 骨架屏：白屏时间是不是可以用骨架屏优化？
>    - 数据预拉取：是否可以用 wx.getBackgroundFetchData？
>
> 3. **出报告**：列出每个因素的耗时占比，给出具体优化建议和优先级
>
> 4. **推动**：跟开发对齐优化方案，定一个可接受的目标（比如首屏 < 2s），优化完后回归验证

---

### 第3题：一个功能在 iOS 上正常，Android 上异常，你怎么排查？

> 1. 先用相同微信版本 + 相同基础库版本确认不是版本差异导致的
> 2. 检查是否用了有平台差异的 API（如日期格式、CSS 属性、JS API）
> 3. 用 Android 真机调试连接开发者工具看具体报错
> 4. 常见坑：
>    - `new Date('2024-01-01')` 在 iOS 上可能返回 Invalid Date，Android 上可能正常
>    - CSS `backdrop-filter` 在低版本 Android 不支持
>    - `wx.saveImageToPhotosAlbum` 权限处理 Android/iOS 流程不同
>    - scroll-view 在 Android 上的滚动表现可能不一致
> 5. 找到根因后给开发指出来，补充到兼容性测试 checklist 中

### 第4题：如果让你搭建小程序的自动化测试体系，你会怎么做？

> 1. **选型**：选择 minium（微信官方）+ Pytest，或 Appium（如果已有 Appium 基础设施）
>
> 2. **分层**：
>    - L1 接口层：直接调后端接口，验证业务逻辑
>    - L2 组件层：小程序组件单元测试
>    - L3 UI 层：minium 自动化操作小程序页面
>
> 3. **用例管理**：
>    - 核心回归用例 100% 自动化
>    - 兼容性遍历用例脚本化
>    - 用例和数据分离（配置文件管理测试账号）
>
> 4. **CI 集成**：
>    - 代码合入触发自动跑接口层 + 组件层
>    - 每日定时跑 UI 层回归
>
> 5. **报告**：
>    - Pytest + allure 生成报告
>    - 失败用例自动截图、录屏

## 八、面试官追问准备

**Q: "你说写过小程序 demo，具体是什么？"**
> （提前准备一个小程序 demo，可以说你做过一个商品列表 + 详情 + 购物车的小程序 demo，覆盖了页面跳转、数据请求、setData、下拉刷新、上拉加载等核心功能，用这个 demo 来验证基础库的兼容性。）

**Q: "你对我们这个岗位的理解是什么？"**
> 这是一个偏底层基础库和客户端质量保障的岗位，不是测某个业务小程序。需要理解微信小程序的运行原理，能写代码开发测试 demo 和自动化用例，同时要跟进基础库和客户端版本发布后的质量问题。对技术深度和测试方法论都有要求。

**Q: "你没有小程序测试经验，你怎么说服我你能胜任？"**
> 虽然我没有专门测过小程序，但我的核心能力是匹配的：第一，我有移动端测试经验，兼容性测试方法论是通用的；第二，我会用 Python/JS 写自动化，minium 框架我能快速上手；第三，我会写前端代码，小程序的 WXML/WXSS/JS 跟 Vue 很像，学习成本低。给我两周时间，我能上手。

**Q: "你觉得测试一个微信基础库的功能，最需要注意什么？"**
> 兼容性是第一位的。基础库是给所有小程序用的，任何改动都可能影响海量小程序。测试时必须考虑：向前兼容（老小程序不能受影响）、向后兼容（新功能在老基础库上要有降级方案）、性能不退化、API 行为变更要明确告知。
