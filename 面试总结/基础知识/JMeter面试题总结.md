# JMeter 面试题总结

---

## 一、基础认知

### 1. JMeter 是什么？用来做什么？

JMeter 是 Apache 开源的性能测试工具，纯 Java 开发。主要用于：
- **性能测试/压测**：模拟高并发，测系统吞吐量和响应时间
- **接口自动化测试**：HTTP、WebService、TCP、JDBC 等协议
- **数据库压力测试**：通过 JDBC 对数据库加压

---

### 2. JMeter 的核心组件有哪些？

```
测试计划（Test Plan）
├── 线程组（Thread Group）         ← 模拟用户
│   ├── 配置元件（Config Element）  ← CSV、HTTP默认值、Header管理器
│   ├── 前置处理器（Pre Processor） ← 请求发之前做处理
│   ├── 取样器（Sampler）           ← 发请求的主体（HTTP、JDBC等）
│   ├── 后置处理器（Post Processor）← 提取响应数据
│   ├── 断言（Assertion）          ← 判断结果对不对
│   ├── 定时器（Timer）            ← 控制请求间隔
│   └── 监听器（Listener）         ← 查看结果、生成报告
├── 逻辑控制器（Logic Controller）  ← 控制执行逻辑（if、循环、仅一次）
└── 函数助手（Functions）           ← ${__property}, ${__CSVRead} 等内置函数
```

**面试要点**：能说出执行顺序——配置元件 → 前置处理器 → 取样器 → 后置处理器 → 断言 → 监听器。

---

### 3. JMeter 的执行流程是怎样的？

**线程组内**，每个线程独立执行，从上到下依次跑完所有取样器。多个线程并发跑。

**关键参数**：
| 参数 | 含义 | 实战值 |
|------|------|--------|
| 线程数 | 并发用户数 | 看需求，100~1000 |
| Ramp-Up 时间 | 多长时间启动完所有线程 | 一般 5~30 秒 |
| 循环次数 | 每个线程跑几遍 | 勾选"永远"就是一直压 |

---

## 二、线程组相关

### 4. setUp 线程组和 tearDown 线程组是什么？

- **setUp 线程组**：最前面执行，一般用来做初始化（登录拿 token、准备测试数据）。只跑 1 次，跑完才执行普通线程组。
- **tearDown 线程组**：最后面执行，用来清理数据（删除测试数据、恢复环境）。
- **普通线程组**：中间的压测主体。

**实际场景**：setUp 里登录 1 次拿到 token 存全局，普通线程组里 100 个线程共用这个 token。

---

### 5. 线程组的 Ramp-Up 时间怎么设置？

Ramp-Up 是启动所有线程的总时长。假设 `线程数=100`，`Ramp-Up=10`：

- 每 0.1 秒启动 1 个线程
- 10 秒内 100 个线程全部启动完毕

**设置原则**：
- 太小：瞬间起大量线程，JMeter 自己先炸了
- 太大：启动太慢，压测没效果
- 一般 5~20 秒，看并发量调整

---

## 三、参数化

### 6. JMeter 怎么参数化？有哪些方式？

| 方式 | 适用场景 | 优缺点 |
|------|---------|--------|
| CSV数据文件设置 | 大量不同数据，每个线程不同参数 | 最常用，但 Windows 编码容易踩坑 |
| 用户变量 | 少量固定参数 | 简单但不灵活 |
| 函数助手 `${__CSVRead}` | 直接函数读 CSV | 不需要配元件，但不够直观 |
| JSR223 PreProcessor 手写 Groovy | CSV 配置不管用时的兜底方案 | 灵活但需要写代码 |
| 随机函数 `${__Random}` | 需要随机值的场景 | 简单但不能控制数据范围 |

---

### 7. CSV数据文件设置的配置要点？

| 参数 | 说明 |
|------|------|
| 文件名 | 绝对路径用正斜杠 `D:/study/users.csv` |
| 文件编码 | UTF-8（记事本另存为时可改） |
| 变量名称 | 逗号分隔，不要有空格：`username,password` |
| 是否带表头 | 第一行是列名就填 True |
| 分隔符 | 英文逗号 `,`，不是中文逗号 `，` |
| 遇到文件结束再次循环 | 一般关掉，100 线程对应 100 条数据 |
| 线程共享模式 | 所有线程 或 当前线程组 |

**常见踩坑**：Windows Excel 保存的 CSV 编码是 ANSI/GBK，JMeter 只认 UTF-8/UTF-16/ASCII，编码不匹配导致变量读不到。解决方法：记事本另存为 UTF-8。

---

### 8. CSV 读了但变量没值怎么办？

1. 加**调试取样器**跑一遍，看变量列表里有没有 `username=`
2. 用**JSR223 PreProcessor + Groovy** 兜底，手动读文件赋值
3. 检查：编码是不是 UTF-8、分隔符是不是英文逗号、层级是不是线程组直接子节点

## 四、接口依赖与令牌传递

### 9. 上一个接口返回的 token，怎么给下一个接口用？

**方式一**：JSON 提取器（推荐，免代码）

登录接口右键 → 后置处理器 → JSON提取器：
| 参数 | 值 |
|------|-----|
| 变量名称 | `token` |
| JSON Path | `$.data.token` |
| 匹配数字 | `1` |

下一个请求的 Header 里：`star-token: Bearer ${token}`

**方式二**：Beanshell PostProcessor

```java
String responseData = prev.getResponseDataAsString();
int s = responseData.indexOf("\"token\":\"") + 9;
int e = responseData.indexOf("\"", s);
vars.put("token", responseData.substring(s, e));
```

**方式三**：JSR223 PostProcessor + Groovy（性能更好）

```groovy
def json = new groovy.json.JsonSlurper().parseText(prev.getResponseDataAsString())
vars.put("token", json.data.token)
```

---

### 10. `${token}` 和 `${__property(token)}` 有什么区别？

| 变量类型 | 作用域 | 存取方式 | 使用场景 |
|---------|--------|---------|---------|
| vars（变量） | 当前线程 | `vars.put("k", v)` → `${k}` | 线程内传递 |
| props（属性） | 全局，跨线程组 | `props.put("k", v)` → `${__property(k)}` | setUp 存 token，所有线程共用 |

**关键**：100 线程并发登录时，每个线程的 `vars` 是独立的，`vars.put` 不会互相覆盖。但如果系统同一账号只认一个有效 token，先登录的会被后登录的踢掉，这时需要用 `setUp + props` 只登录一次。

---

### 11. 100 线程并发登录，token 互相踢掉怎么办？

**原因**：同账号每登录一次新 token 覆盖旧 token，前面的线程拿到的 token 就过期了。

**解决**：
1. `setUp 线程组`：1 个线程登录，`props.put("token", token)` 存全局
2. 普通线程组：100 线程共用，Header 里用 `${__property(token)}`
3. 或者 CSV 存 100 个不同账号，每个线程独立登录

## 五、提取器

### 12. 正则表达式提取器和 JSON 提取器的区别？

| 维度 | 正则表达式提取器 | JSON 提取器 |
|------|----------------|-------------|
| 适用场景 | 任何文本响应 | JSON 格式响应 |
| 语法 | `"token":"([^"]+)"` | `$.data.token` |
| 易用性 | 需要懂正则 | 更直观简洁 |
| 性能 | 略好 | 需要解析 JSON |
| 多值提取 | 可以用模板控制 | Match No. 控制 |

**建议**：JSON 响应用 JSON 提取器，HTML/XML/纯文本用正则。

---

### 13. JSON 提取器的 Match No.（匹配数字）怎么用？

| 值 | 含义 |
|----|------|
| 0 | 随机取一个 |
| 1 | 取第 1 个匹配 |
| 2 | 取第 2 个匹配 |
| -1 | 匹配所有，存成 `token_1`、`token_2`...，`token_matchNr` 是总数 |

## 六、断言

### 14. JMeter 有哪些断言？常用哪个？

| 断言类型 | 用途 |
|---------|------|
| 响应断言 | 看响应里是否包含指定字符串，最常用 |
| JSON 断言 | JSON Path + 期望值，适合接口自动化 |
| 大小断言 | 响应 body 是否在指定大小范围内 |
| 持续时间断言 | 响应时间是否超过阈值（超了就标记失败） |
| Beanshell 断言 | 自定义更复杂的断言逻辑 |

**压测常用**：响应断言 + 持续时间断言。
**自动化常用**：JSON 断言 + 响应断言。

---

## 七、定时器

### 15. 定时器的作用？常用哪几种？

定时器控制请求发送的**节奏**，模拟真实用户行为。

| 定时器 | 作用 | 使用场景 |
|--------|------|---------|
| 固定定时器 | 每次请求等固定毫秒 | TPS 控制 |
| 高斯随机定时器 | 随机等待，正态分布 | 模拟用户思考时间 |
| 同步定时器 | 凑够 N 个线程再一起发 | 并发测试/秒杀场景 |
| 常数吞吐量定时器 | 控制 TPS/min | 精确控制吞吐量 |

**面试考点**：同步定时器是**集合点**，比如设置 100，就会等凑够 100 个线程再一起发出，模拟秒杀瞬间。

---

## 八、逻辑控制器

### 16. 常见的逻辑控制器有哪些？

| 控制器 | 作用 |
|--------|------|
| 仅一次控制器 | 里面的请求只执行一次（不管循环多少次） |
| 循环控制器 | 里面的请求循环执行指定次数 |
| 如果（If）控制器 | 条件判断，满足才执行 |
| 事务控制器 | 把多个请求包成一个事务，统一计时 |
| 交替控制器 | 每次轮流选择其中的一个请求执行 |
| 随机控制器 | 随机选一个请求执行 |

---

## 九、监控与报告

### 17. JMeter 怎么看结果？聚合报告怎么读？

**常用监听器**：

| 监听器 | 用途 |
|--------|------|
| 查看结果树 | 调试用，看每个请求的请求体、响应体 |
| 聚合报告 | 看统计：样本数、平均RT、中位数、95线、99线、TPS、错误率 |
| 汇总报告 | 和聚合报告类似，少一些指标 |
| 图形结果 | 曲线图看响应时间趋势 |
| TPS 图 | 看吞吐量变化曲线 |

**注意**：压测时关掉查看结果树等监听器，只保留聚合报告。监听器本身吃性能。

---

### 18. 聚合报告各列含义？

| 指标 | 含义 |
|------|------|
| Samples | 发了多少次请求 |
| Average | 平均响应时间（ms） |
| Median | 中位数（50%的请求在此时间内完成） |
| 95 Line | 95%的请求在此时间内完成 |
| 99 Line | 99%的请求在此时间内完成 |
| Min / Max | 最小/最大响应时间 |
| Error % | 错误率 |
| Throughput | 吞吐量，每秒处理多少请求 |
| Received KB/sec | 每秒接收的响应数据大小 |

**关注重点**：95线 > 平均 > 中位数，因为平均会被快请求拉低。

---

### 19. GUI 模式和命令行模式有什么区别？

| 维度 | GUI 模式 | 命令行模式 |
|------|---------|-----------|
| 用途 | 脚本编写、调试 | 正式压测执行 |
| 性能 | 消耗大量资源（UI 渲染） | 性能好 |
| 命令 | 双击打开 | `jmeter -n -t script.jmx -l result.jtl -j jmeter.log` |

**面试金句**：正式压测一定是命令行跑，GUI 只用来调试脚本。

## 十、分布式压测

### 20. JMeter 分布式压测怎么搭？

单机瓶颈（内存/网络）不够时，用多台机器一起发请求：

```
主控机（Master）  → 控制脚本、收集结果
从机1（Slave）    → 真正发请求
从机2（Slave）    → 真正发请求
从机3（Slave）    → 真正发请求
```

**配置步骤**：
1. Master 和 Slave 在同一网段
2. Slave 端启动 `jmeter-server`
3. Master 的 `jmeter.properties` 里配置 slave IP
4. Master 端启动测试，结果回传汇总

**注意**：分布式压测不是简单的 `N × 单机并发`，因为 Master 收集结果和 Slave 通信也有开销。

## 十一、Beanshell vs JSR223

### 21. Beanshell 和 JSR223 怎么选？

| 维度 | Beanshell | JSR223 + Groovy |
|------|-----------|-----------------|
| 性能 | 一般 | **更好**，接近原生 Java |
| 语法 | Java 语法 | Groovy（Java 超集） |
| JSON 解析 | 需要导入 json.jar | Groovy 内置 `JsonSlurper` |
| 社区推荐 | 旧项目在用 | **生产推荐** |

**面试金句**：企业实战都推荐 JSR223 + Groovy，性能更好，内置 JSON 解析，不需要额外导包。

## 十二、常见问题排查

### 22. JMeter 跑着跑着自己先卡死了怎么办？

| 原因 | 解决 |
|------|------|
| GUI 模式 + 高并发 | 改成命令行跑 |
| 监听器太多 | 关掉查看结果树，只留聚合报告 |
| 内存不够 | 改 `jmeter.bat` 里 `HEAP` 参数，加大堆内存 |
| 本机带宽打满 | 上分布式 |
| 太多线程创建开销 | 线程数不要太大，考虑用 Ramp-Up |

---

### 23. 压测结果和预期差很多怎么办？

排查顺序：
1. 先看网络：是不是本机压远程服务器，本机带宽打满了（优先考虑服务器和压测机在同一内网）
2. 看被测服务日志：接口有没有报错
3. 看服务器监控：CPU、内存、数据库连接数，找到瓶颈在哪
4. 看 JMeter 自己：本机资源消耗情况，是不是工具先扛不住了
5. 检查脚本：断言、变量替换有没有问题

## 十三、实战场景问答

### 24. 你怎么用 JMeter 做登录+业务接口的压测？

```
setUp线程组（1线程）
├── 登录接口
│   └── JSR223 PostProcessor → props.put("token", token)

普通线程组（100线程）
├── HTTP信息头管理器 → star-token: Bearer ${__property(token)}
├── 业务接口A
├── 业务接口B
└── 聚合报告
```

**要点**：setUp 只登录一次拿 token 存全局，压主体用 100 线程共用。避免同账号反复登录互相踢 token。

---

### 25. 怎么测试秒杀/并发超卖？

1. 同步定时器：设置集合点，凑够 N 线程同时发
2. 线程数设大一点，比如 500
3. 循环只设 1 次
4. 看返回结果：有没有超卖（库存负数）
5. 配合断言的计数，统计成功多少笔

```groovy
// JSR223 断言检查超卖
def json = new groovy.json.JsonSlurper().parseText(prev.getResponseDataAsString())
if (json.data.stock < 0) {
    prev.setSuccessful(false)
    prev.setResponseMessage("超卖了！库存变负数")
}
```

### 26. JMeter 和其他压测工具比优劣在哪？

| 工具 | 优势 | 劣势 |
|------|------|------|
| JMeter | 免费开源、UI 简单易上手、插件丰富、协议支持广 | 高并发下资源消耗大、分布式配置麻烦 |
| Locust | Python 写脚本灵活、单机并发能力更强 | 只支持 HTTP，适用范围窄 |
| Gatling | 性能比 JMeter 好、基于 Scala、报表漂亮 | 上手门槛高、需要写代码 |
| ApiPost | 快速压测、操作简单 | 并发能力有限、适合简单场景 |

**谁的岗位要求**：大多数公司用 JMeter，因为免费 + UI + 够用。

---

### 27. 压测脚本写了断言但没报错，上线后压测出问题？

**可能原因**：
- 断言只判断了 HTTP 200，但业务逻辑返回了错误（`{"code":500}`），你没校验业务状态码
- 解决：断言不光看 HTTP 状态码，还要校验返回体里的业务 `code`

```
响应断言设置：
  - 响应文本 → 包含 → "code":0
  - 响应代码 → 等于 → 200
```

两条同时设，一个判断 HTTP 正常，一个判断业务正常。

## 十四、关键数值得记住

| 概念 | 面试要点 |
|------|---------|
| JMeter 是 Java 写的 | 协议支持广，分布式用 RMI 通信 |
| vars vs props | vars 线程级，props 全局 |
| setUp / tearDown | setUp 准备数据，tearDown 清理 |
| 执行顺序 | 配置→前置→取样器→后置→断言→监听 |
| 聚合报告核心指标 | 95线、错误率、TPS |
| CSV 参数化 | 编码 UTF-8，分隔符英文逗号 |
| JSON 提取器 | `$.data.token`，Match No.=1 |
| 后置处理器 | JSON 提取器 > 正则提取器 > JSR223 > Beanshell |
| 命令行 | `jmeter -n -t test.jmx -l result.jtl` |
| 同步定时器 | 集合点，用于并发测试 |
