# Test Cases: 支付过程网络中断测试

## Overview
- **Feature**: 支付系统 - 网络中断场景测试
- **Requirements Source**: 用户需求 - 验证支付过程中网络中断时数据一致性和幂等性
- **Test Coverage**: 覆盖支付流程各关键节点的网络中断、订单状态一致性、重复回调处理
- **Last Updated**: 2026-04-12

## Test Case Categories

### 1. Error Handling Tests (网络中断场景)

#### TC-ERR-001: 支付请求发出后，响应返回前网络中断
- **Requirement**: 支付请求已发出到支付网关，但未收到响应时网络中断，系统需正确处理订单状态
- **Priority**: High
- **Preconditions**:
  - 用户已选择商品进入支付页面
  - 账户余额充足
  - 测试环境可模拟网络中断
- **Test Steps**:
  1. 用户确认支付，点击"立即支付"按钮
  2. 在请求发送到支付网关后，立即断开网络（使用浏览器离线/charles断网/飞行模式）
  3. 等待30秒后恢复网络
  4. 刷新页面查看订单状态
  5. 查看数据库中订单记录和支付流水
- **Expected Results**:
  - 订单状态保持"待支付"或"支付中"，不能变成"支付失败"也不能变成"支付成功"
  - 系统未生成重复支付单
  - 网络恢复后，系统能正确轮询或接收支付网关回调更新订单状态
  - 用户可以重新发起支付
- **Postconditions**: 测试完成后恢复网络，清理测试订单

#### TC-ERR-002: 用户已支付成功，支付网关回调时网络中断
- **Requirement**: 用户在支付网关完成支付，但回调通知商户时网络中断，需保证最终一致性
- **Priority**: High
- **Preconditions**:
  - 商户系统与支付网关回调网络可人为中断
  - 测试订单已创建
- **Test Steps**:
  1. 发起支付，在支付网关层面完成支付
  2. 在支付网关准备回调商户时，断开商户服务器网络
  3. 保持网络中断5分钟，模拟回调失败
  4. 恢复网络，等待重试机制执行
  5. 检查订单状态
- **Expected Results**:
  - 支付网关会重试回调（根据配置的重试策略）
  - 网络恢复后回调成功，订单状态正确更新为"支付成功"
  - 多次重试回调满足幂等性，不会重复处理导致重复入账
- **Postconditions**: 恢复网络，清理测试数据

#### TC-ERR-003: 支付过程中客户端网络完全断开，用户重新进入页面
- **Requirement**: 支付中断后用户重新进入订单页面，应显示正确状态并允许重试
- **Priority**: High
- **Preconditions**:
  - 用户登录APP/网页
  - 已创建待支付订单
- **Test Steps**:
  1. 点击支付，跳转支付页面
  2. 支付过程中断开客户端网络
  3. 关闭APP/浏览器，重新打开进入订单详情页
  4. 查看订单状态显示
- **Expected Results**:
  - 正确显示订单当前状态（待支付/支付中）
  - 不显示错误的"支付成功"或"支付失败"
  - 提供"重新支付"按钮允许用户重试
- **Postconditions**: 清理测试订单

#### TC-ERR-004: 分阶段支付 - 扣款成功后通知阶段网络中断
- **Requirement**: 支付网关已扣款成功，但通知商户时网络中断，资金和订单状态需一致
- **Priority**: High
- **Preconditions**:
  - 对接第三方支付网关
  - 可在回调阶段断网
- **Test Steps**:
  1. 创建测试订单，金额匹配测试余额
  2. 在支付网关完成支付，确认扣款成功（查询支付网关对账单）
  3. 在回调发生时断开网络，阻止回调到达商户系统
  1. 商户系统发起主动查询（轮询/定时对账）
  2. 检查商户系统订单状态是否更新
- **Expected Results**:
  - 主动查询能获取到支付网关已成功的状态
  - 订单状态更新为"支付成功"，资金流水正确入账
  - 不会因为未收到回调而错误退款
- **Postconditions**: 恢复网络，对账确认一致性

#### TC-ERR-005: 网络抖动导致数据包丢失，支付请求半完成
- **Requirement**: 网络不稳定导致请求包不完整，系统应能识别并处理
- **Priority**: Medium
- **Preconditions**:
  - 使用tc命令或charles模拟丢包
- **Test Steps**:
  1. 配置网络丢包率100%
  2. 用户点击支付发起请求
  3. 清除丢包配置，恢复网络
  4. 检查订单状态和系统日志
- **Expected Results**:
  - 系统识别到请求超时/不完整
  - 订单保持一致状态，不会出现脏数据
  - 连接池/线程池正常释放，无资源泄漏
- **Postconditions**: 清除网络丢包配置

#### TC-ERR-006: 支付完成后连续多次重试回调（网络恢复后）
- **Requirement**: 验证幂等性，多次回调不能重复处理
- **Priority**: High
- **Preconditions**:
  - 支付网关支持手动重发回调
  - 测试订单已支付成功
- **Test Steps**:
  1. 订单支付成功，第一次回调成功，订单已变更为成功
  2. 手动调用支付网关重发5次相同回调
  3. 检查数据库订单状态和流水记录
  4. 检查账户余额/积分增减
- **Expected Results**:
  - 只有第一次回调有效，后续回调被幂等处理
  - 订单状态保持"支付成功"不变
  - 资金只入账一次，不会重复增加用户余额/积分
  - 系统日志正确记录重复回调并标记为已处理
- **Postconditions**: 清理测试数据

### 2. State Transition Tests

#### TC-ST-001: 支付中 → 网络中断 → 恢复 → 支付成功 状态流转
- **Requirement**: 订单状态机正确处理网络中断后的状态流转
- **Priority**: High
- **Preconditions**:
  - 订单状态机已定义：待支付 → 支付中 → 支付成功/支付失败
- **Test Steps**:
  1. 创建订单，初始状态=待支付
  2. 发起支付，状态变为支付中，此时断网
  3. 支付网关完成扣款，恢复网络后回调到达
  4. 检查最终订单状态
- **Expected Results**:
  - 断网时状态保持"支付中"
  - 回调到达后正确转换为"支付成功"
  - 无非法状态转换（如从支付中直接变为失败）
- **Postconditions**: 清理测试订单

#### TC-ST-002: 网络中断超时后订单关闭，用户重试支付
- **Requirement**: 支付中超时关闭后，用户可以重新发起支付
- **Priority**: Medium
- **Preconditions**:
  - 系统配置支付超时时间（如15分钟），超时自动关闭订单
- **Test Steps**:
  1. 发起支付进入支付中状态，断网
  2. 等待超过超时时间，触发超时关闭任务
  3. 检查订单状态
  4. 用户重新下单发起支付
  5. 完成支付检查结果
- **Expected Results**:
  - 超时后订单正确关闭，状态变为"已关闭"
  - 库存回滚正确释放
  - 用户可重新下单并完成支付
  - 无重复扣款
- **Postconditions**: 清理测试数据

### 3. Edge Case Tests

#### TC-E-001: 网络中断恢复后，用户重复点击支付按钮
- **Requirement**: 网络恢复后用户重复点击，系统应防重复提交
- **Priority**: Medium
- **Preconditions**:
  - 用户待支付订单
  - 可模拟断网再恢复
- **Test Steps**:
  1. 点击支付后立即断网
  2. 用户看不到结果，快速连续点击5次支付按钮
  3. 恢复网络
  4. 检查生成了几个支付单，扣款几次
- **Expected Results**:
  - 防重复提交机制生效，只生成一个有效支付单
  - 只扣款一次
  - 多余的点击被拦截并提示"支付处理中，请稍候"
- **Postconditions**: 核对流水，清理数据

#### TC-E-002: 分布式场景 - 扣减库存成功，扣款前网络中断
- **Requirement**: 分布式事务一致性，先扣库存再扣款，扣款时断网需保证最终一致
- **Priority**: High
- **Preconditions**:
  - 库存和支付分离在不同服务
  - 使用消息队列/异步补偿机制
- **Test Steps**:
  1. 用户下单，库存服务扣减库存成功
  2. 库存扣减完成后，调用支付服务前网络中断
  3. 恢复网络
  4. 检查库存和支付状态一致性
- **Expected Results**:
  - 补偿机制触发（消息重试/定时对账）
  - 最终要么支付成功，库存保持扣减；要么库存回滚，支付失败
  - 不会出现"库存扣了但没扣款"或"扣款了但库存没扣"的不一致
- **Postconditions**: 恢复库存数据

## Notes

### 核心测试要点：
1. **订单状态一致性** - 无论何时断网，订单状态、资金流水、库存三者最终必须一致
2. **幂等性处理** - 支付回调必须支持幂等，网络重试不会导致重复入账
3. **补偿机制** - 异步支付需要有定时对账/主动查询机制来保证最终一致性
4. **防重复提交** - 用户重复点击不会生成多个支付单

### 实际测试建议：
- 优先测试核心路径：请求发出后断网、回调时断网、幂等性
- 在测试环境使用charles/tc命令模拟，预发布环境可以用拔网线/飞行模式真实测试
- 重点验证：资金不能错，不能少给用户发货也不能多扣钱
- 对账是最后一道防线，一定要测试对账流程能否自动修正不一致
